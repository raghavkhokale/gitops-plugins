# /p1as:patch

Specialization of CLAUDE.md **Workflow B: Repository / Cluster modification** for the patch case. Follow Workflow B in full (phases B1a–B5) — this file documents only the patch-specific edit-point heuristic within phase B1c.

**Input:** Customer, env, and a description of what the patch should do (e.g. "increase the Nginx public header size to 64 KB for deloitte dev"). The skill determines the edit point from the discovery output.

---

## Phase B1b — discovery

Use the **Discovery methodology** in CLAUDE.md (Workflow B). No hardcoded reads — render both tiers, search by kind+name, trace the kustomization graph backward.

**First check the "Skip discovery when the user has already done it" rule** (top of the methodology section). If the user has provided explicit instructions, a runbook URL, or a ticket with detailed steps, skip the methodology (or do partial discovery) and follow what they said. Don't render the manifest if the user has already specified what to change and where.

---

## Phase B1c — edit-point heuristic for patches

After the Discovery methodology has located the resource and the input file(s) that contributed it, choose the edit point:

- **If the customer already overrides the resource** in their CSR (a kustomize patch entry or a Helm values override exists), the new change goes there. Find it via the graph traversal — do not assume which file.
- **If no existing override** and the resource is platform-tier (kustomize-only): add a kustomize patch at the appropriate graph node (typically a `custom-patches.yaml` in or referenced by the relevant kustomization).
- **If no existing override** and the resource is microservice-tier (helm-rendered): add a Helm values override at the appropriate values-files node, referenced by the microservice's `helmCharts.additionalValuesFiles` chain.
- **If the resource is hand-written** (custom-resources/, not generated by helm or kustomize composition), edit that file directly.

The graph traversal output tells you exactly which file is the edit point. Do not hardcode it.

---

## Phase B3 (apply locally + diff + approve) — patch specifics

Use the `Edit` tool on the edit-point file inside the working branch from Phase B2. Do NOT call `mcp__server__patch_custom_confirm` or `mcp__server__patch_kust_confirm` — those bundle write+commit+push+MR and violate Workflow B.

After writing: run `git diff`, show output, ask "Does this diff look right? Reply 'approved' to commit, or tell me what to change." **END TURN, wait.** Per CLAUDE.md "Turn boundaries", this is a mandatory turn boundary.

---

## Resuming an interrupted flow

- Pending preview from Phase B1 (held in `_approval` store, 30-min TTL) → use `/p1as:resume`
- Already on a working branch with uncommitted changes → resume from Phase B3 (re-show diff, re-ask)
- Already pushed but no MR → resume from Phase B4 MR creation

## Out of scope

This skill does NOT watch ArgoCD sync or do post-apply health checks — those require the `cluster` category, which is currently disabled.
